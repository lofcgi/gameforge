gameforge 하네스의 구조

이 문서를 읽으면 gameforge가 어떤 부품으로 이루어졌고 왜 그렇게 나눴는지 설명할 수 있어요. 비슷한 하네스를 직접 설계할 때 "무엇을 문서로 두고, 무엇을 명령으로 만들고, 무엇을 막을지"를 정하는 기준으로 쓸 수 있어요.

하네스가 왜 필요한지는 하네스가 필요한 이유에서 먼저 읽으세요.

세 개의 층

gameforge는 세 층으로 나뉘어요. 위층은 에이전트에게 무엇을 언제 할지 알려 주고, 아래층은 그 일을 실제로 실행하고 측정해요.

┌─────────────────────────────────────────────────────────────┐
│ 플러그인 층   harness/skills, harness/agents, harness/hooks │
│   스킬 13개        단계별 절차 문서 (언제, 어떤 순서로)       │
│   서브에이전트 2개  blind-judge, playtest-reviewer           │
│   훅 1개           guard.py (하면 안 되는 행동을 막는다)      │
└───────────────────────────┬─────────────────────────────────┘
                            │ 스킬이 gf 명령을 부른다
┌───────────────────────────▼─────────────────────────────────┐
│ CLI 층   harness/tools/gf   (Python, 실행 파일 gf)           │
│   gen 생성 · post 후처리 · blender 3D 정리                   │
│   engine 실행·캡처·봇 · ref 레퍼런스 · judge 심사 · check 검사 │
└───────────────────────────┬─────────────────────────────────┘
                            │ gf init 이 복사하고, gf engine 이 실행한다
┌───────────────────────────▼─────────────────────────────────┐
│ 템플릿 층   harness/templates                                │
│   godot-2d · godot-3d · web-2d · web-3d  + 브리지            │
└─────────────────────────────────────────────────────────────┘

이렇게 나눈 이유는 층마다 바뀌는 속도가 다르기 때문이에요.

  • 절차는 글로 둬요. 스킬은 Markdown 문서라서 사용자의 피드백을 받으면 바로 고칠 수 있어요.
  • 측정은 코드로 둬요. 픽셀 격자를 맞추거나 음악의 이음매를 재는 일은 에이전트가 매번 즉석에서 짜면 결과가 달라져요. gf 명령으로 고정하면 같은 입력에 같은 결과가 나오고, 테스트를 붙일 수 있어요. harness/tools/tests/의 단위 테스트는 이 문서를 쓰며 돌렸을 때 282개가 통과했어요(인계 기록 시점에는 279개였어요).
  • 게임 뼈대는 템플릿으로 둬요. 템플릿에 든 브리지 덕분에 어떤 게임이든 같은 명령으로 실행하고 캡처할 수 있어요.

플러그인 층은 CLI 층을 다 만든 뒤 마지막에 썼어요. 스킬에 적는 명령을 실제 --help 출력과 대조하기 위해서예요(세션 기록).

단계와 단계 승인

하네스는 제작을 여섯 단계로 나누고, 단계마다 결과물을 파일로 보여 준 뒤 사용자의 승인을 받아야 다음 단계로 넘어가요.

 plan ──► look ──► graybox ──► assets ──► polish ──► publish
  │        │          │           │          │          │
  └────────┴──────────┴─── 단계마다 ──────────┴──────────┘
        결과물을 보여 준다 → 사용자가 승인한다 → gf state approve
단계 사용자가 보는 결과물
plan 설계 요약 design/brief.md
look 고른 레퍼런스, 기준 화면, 아트 디렉션
graybox 도형만으로 플레이할 수 있는 빌드
assets 그림, UI, 소리가 들어간 화면
polish 손맛, 가독성, 첫 1분, 성능을 다듬은 빌드
publish 배포용 빌드와 공개 글 초안

현재 단계와 승인 기록은 게임 폴더의 .gf/state.json에 남아요. 예를 들어 cat-angler의 이 파일에는 plan과 look을 승인한 시각과 메모가 들어 있어요(games/cat-angler/.gf/state.json).

단계별 스킬과 생기는 파일은 단계별 스킬과 산출물에 표로 정리했어요.

근거 규칙과 훅

근거 규칙은 "실행해서 본 것만 말한다"예요. 에이전트가 "고쳤다"고 말하려면 그 변경 뒤에 돌린 결과 파일이 있어야 해요(harness/skills/gf-verify/SKILL.md).

규칙만 적어 두면 에이전트가 건너뛸 수 있어서, 훅이 같은 내용을 강제해요. 훅(harness/hooks/guard.py)은 에이전트가 도구를 쓰기 직전에 실행되고, .gf 폴더가 있는 게임 프로젝트 안에서만 동작해요. 훅이 막는 행동은 네 가지예요(harness/README.md).

훅이 막는 행동 막는 이유
근거 없는 gf state approve 마지막 변경 뒤에 통과한 스모크 테스트와 스크린샷이 없으면 승인할 수 없어요
.env 읽기와 출력 생성 API 키가 대화나 기록에 남지 않게 해요
승인·심사·비용 기록과 브리지 파일을 손으로 고치거나 지우기 불리한 기록을 지우거나 검사를 약하게 만드는 길을 막아요
심사자가 심사 폴더 밖의 파일 읽기 심사자가 어느 쪽이 수정 후인지 알아내지 못하게 해요

튜토리얼에서 설계 요약 없이 승인 근거를 검사하면 실제로 이렇게 실패해요.

{"ok": false, "error": "'plan' 단계를 승인할 근거가 부족하다: design/brief.md 가 없거나 비었다 → gf-plan 절차로 설계 요약을 쓰고 사용자에게 보여 준 뒤 승인한다.", "stage": "plan", "problems": ["design/brief.md 가 없거나 비었다"], "hints": ["gf-plan 절차로 설계 요약을 쓰고 사용자에게 보여 준 뒤 승인한다."]}

2D와 3D를 한 뼈대로 다루는 방식

단계, 검증, 승인 절차는 2D와 3D가 똑같아요. 달라지는 것은 assets 단계의 스킬뿐이에요. 프로젝트를 만들 때 고른 스타일에 따라 에이전트가 읽는 스킬이 바뀌어요.

스타일 (gf init --style) 에셋 스킬 만드는 방법
pixel gf-assets-pixel 단색 배경에 생성 → 크로마 → 격자 맞춤 → 팔레트 적용 → 1배 검사
2d gf-assets-2d 기준 화면을 참조로 생성 → 배경 제거 → 같은 배율로 줄이기
3d-code, 3d-gen gf-assets-3d 코드로 그리거나, 컨셉 이미지 → 3D 모델 → Blender 정리

UI(gf-ui)와 소리(gf-audio) 스킬은 모든 스타일이 함께 써요.

역할로 부르는 생성 모델

gf gen 명령은 모델 이름 대신 역할 이름을 받아요. 실제 모델 ID는 설정 파일에만 있어요.

역할 하는 일 2026-11-22 기준 기본 모델
image.concept 프롬프트로 이미지 만들기 fal-ai/nano-banana-2
image.edit 참조 이미지를 받아 고치기 fal-ai/nano-banana-2/edit
video.sprite 정지 스프라이트를 움직이는 영상으로 fal-ai/kling-video/v3/turbo/standard/image-to-video
model3d.gen 이미지에서 3D 모델 만들기 tripo3d/p2/image-to-3d
audio.sfx, audio.music 효과음, 배경음악 elevenlabs/sound-effects/v3, elevenlabs/music/v2.5

전체 목록은 harness/tools/gf/core/defaults.toml에 있어요. 이렇게 한 이유는 두 가지예요.

  • 모델은 자주 은퇴해요. 모델이 바뀌면 설정 한 줄만 고치면 돼요. 게임 폴더의 .gf/config.toml이 기본값을 덮어써요.
  • 입력 필드는 모델마다 달라요. 에이전트가 필드를 추측하지 않도록 gf fal schema <모델 ID>로 실제 스키마를 읽게 했어요(harness/AGENTS.md).

생성 제공자는 fal 하나로 통일했어요. 키 하나, 단가 조회 API 하나로 모든 호출의 추정 비용을 같은 방식으로 계산할 수 있어요.

명령의 출력 규약

모든 gf 명령은 같은 형식으로 끝나요(harness/AGENTS.md).

  • 성공하면 종료 코드 0과 함께 표준 출력 마지막 줄에 JSON 한 줄을 내요: {"ok": true, "files": [...], "cost_usd": 0.0, ...}
  • 실패하면 0이 아닌 종료 코드와 {"ok": false, "error": "..."}를 내요.
  • 실패했을 때 조용히 다른 방법으로 빠지지 않아요. 오류 문장이 대신 쓸 명령을 알려 줘요.

이 규약 덕분에 에이전트는 어떤 명령이든 마지막 줄만 읽으면 결과와 생긴 파일을 알 수 있어요. 여러 제작 에이전트가 명령을 따로 만들어도 서로의 출력을 읽을 수 있는 것도 이 규약 때문이에요.

게임 폴더에 생기는 하네스 파일

하네스는 결과를 모두 게임 폴더 안에 써요.

<게임 폴더>/
  .gf/state.json      단계, 엔진, 스타일, 승인 기록
  .gf/config.toml     역할 → 모델 ID, 호출당 비용 한도
  .gf/ledger.jsonl    비용 기록
  .gf/judge/          심사 쌍의 정답 대응표 (심사자와 메인 세션은 읽지 않는다)
  gf/                 브리지
  design/             설계 요약, 아트 디렉션, 기준 화면
  references/         레퍼런스
  assets/raw/         원본
  assets/game/        게임용 에셋 (게임 코드는 여기만 읽는다)
  captures/           스크린샷, 봇 결과, 심사 폴더, 측정 결과

assets/raw/와 assets/game/을 나눈 것이 중요해요. 생성 모델이 내놓은 원본은 그대로 게임에 들어가지 못하고, 후처리 사슬을 통과한 파일만 assets/game/에 들어가요. gf check assets가 이 경계를 검사해요.

정리

  • 절차는 스킬 문서, 측정은 gf 명령, 금지는 훅이 맡아요.
  • 단계마다 사용자가 결과물을 보고 승인하고, 훅이 근거 없는 승인을 막아요.
  • 스타일이 달라도 뼈대는 같고 에셋 스킬만 바뀌어요.
  • 모델은 역할로 부르고, 명령은 마지막 줄 JSON으로 답해요.
