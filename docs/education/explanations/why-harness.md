# 하네스가 필요한 이유

> 문서 유형: 설명

이 문서를 읽으면 "프롬프트를 잘 쓰면 되지 않나"라는 질문에 답할 수 있어요. gameforge는 처음부터 하네스를 만들려고 시작한 프로젝트가 아니에요. 최근 한 달 동안 혼자서 AI로 게임을 만든 사람들이 실제로 무엇을 했는지 조사했고, 품질을 가른 행동이 전부 "에이전트가 스스로는 하지 않는 일"이었기 때문에 그 일을 장치로 고정했어요. 조사에서 찾은 사실과 그 사실이 어떤 장치가 됐는지를 차례로 설명해요.

용어가 낯설면 [용어집](../glossary.md)을 먼저 보세요.

## 조사한 방법

사용자의 첫 질문은 "혼자서 AI로 품질 좋은 게임을 만드는 사람들은 실제로 어떻게 하는가"였고, 조건은 최근 한 달(2026-10-22 ~ 2026-11-22) 자료만 쓰는 것이었어요. 조사는 세 가지 규칙으로 진행했어요.

- **주제별로 나눠 동시에 조사했어요.** 조사 노트가 주제별 파일로 남아 있어요(`research_notes/AI 1인 게임 개발 방법론/01_검증된_성공사례.md` ~ `14_Reddit_데스크톱조사.md`). 주제별 조사자를 따로 띄우고 보고서 작성자가 합쳤어요(세션 기록).
- **기간 밖 자료와 검증되지 않은 수치에 표시를 붙였어요.** 보고서는 [1차], [자가 보고], [추정], [배경·기간 외] 같은 표기 규칙을 맨 앞에 정의해요.
- **읽지 못한 것은 읽지 못했다고 적었어요.** Reddit과 X는 평범한 방법으로는 읽히지 않았어요. 공개 API, 영상 자막, 사용자가 로그인한 브라우저를 차례로 시도했고(노트 07~14번 파일 이름에 그 경로가 남아 있어요), 끝까지 읽지 못한 것은 보고서의 "확인하지 못한 것" 절에 적었어요. 예를 들어 최종 보고서는 Reddit 스레드를 직접 연 것이 5건뿐이라고 밝히고, 나머지에는 링크를 지어내지 않았어요.

조사 도중 사용자가 선정 기준을 바꿨어요. 첫 보고서(`reports/AI 1인 게임 개발 방법론.md`)의 기준은 "AI 중심 + 1인 + 수치로 검증된 흥행"이었고, 최종 보고서(`reports/AI 풀제작 고퀄 1인 게임 방법론 2.md`)의 기준은 "플레이 가능 + 1인 기획 + AI 풀 제작 + 관찰되는 품질"이에요. 판매 실적은 조건에서 뺐어요. 기준이 바뀌자 보고서를 다시 썼어요.

## 조사에서 찾은 사실

두 보고서의 결론을 줄이면 다섯 가지예요.

1. **상업적으로 검증된 사례는 한 건뿐이었어요.** 첫 보고서의 기준을 모두 충족한 것은 Steam 게임 한 건이었고, 그 제작자는 약 1년 동안 직접 플레이하며 갈아엎기를 반복했어요.
2. **화제가 된 3D 시연은 전부 무료 브라우저 빌드였어요.** 판매나 플레이어 수치가 없었어요.
3. **제작자들은 생성 도구보다 검증 장치를 설명했어요.** 최종 보고서는 여러 사람의 방법을 겹쳐 "룩 고정 → 설계 → 자가 실행 → 블라인드 심사 → 사람 플레이"라는 공통 흐름을 뽑았어요.
4. **테스트 통과는 화면이 맞다는 뜻이 아니었어요.** 보고서가 인용한 게임잼 기록에는 테스트가 전부 통과했는데 첫 프레임이 검은 화면이었던 사례, 에이전트가 고치지 않은 것을 "fixed"라고 보고한 사례가 있어요.
5. **넓은 범위와 높은 충실도를 함께 갖춘 1인 AI 제작물은 찾지 못했어요.** 캐릭터 애니메이션, 소리, UI는 제작자 본인들이 약점으로 꼽았어요.

이 조사에도 한계가 있어요. 최종 보고서는 어떤 게임도 직접 플레이하지 않았고 플레이 링크를 한 건도 열어 보지 않았다고 적어요. 그래서 "품질이 높다"는 판단은 게시물, 참여 수치, 답글을 읽은 것이에요.

## 프롬프트만으로 부족한 까닭

위 다섯 가지를 다시 보면 품질을 만든 행동은 모두 에이전트에게 불편한 일이에요.

- 기준 화면을 먼저 고정하면 에이전트는 "대충 예쁜 그림"으로 넘어갈 수 없어요.
- 게임을 실제로 실행해 스크린샷을 보면 "코드상으로는 맞다"는 말이 통하지 않아요.
- 맥락 없는 심사자가 평가하면 자기가 고친 화면을 스스로 칭찬할 수 없어요.
- 사람이 플레이하면 "봇이 깼으니 완성"이라고 할 수 없어요.

프롬프트에 "꼭 실행해서 확인해"라고 적는 것은 부탁이에요. 대화가 길어지거나 작업이 급해지면 에이전트는 부탁을 건너뛰어요. 하네스는 같은 내용을 **건너뛸 수 없는 구조**로 바꿔요. 절차는 스킬 문서로 주고, 실행과 측정은 명령으로 만들고, 증거 없이 다음 단계로 가는 행동은 훅이 막아요.

## 사실이 장치가 된 과정

조사에서 찾은 사실마다 하네스에 대응하는 장치가 있어요.

| 조사에서 찾은 사실 | 하네스의 장치 | 저장소 위치 |
|---|---|---|
| 룩을 먼저 고정한 제작자의 결과가 일관됐다 | `look` 단계. 후보 여러 장 중 사용자가 고른 한 장을 기준 화면으로 고정하고 아트 디렉션을 쓴다 | `harness/skills/gf-look/SKILL.md` |
| 설계 문서는 양보다 순서가 문제다 | `plan` 단계. 구현 전에 결정을 닫고 설계 요약을 승인받는다 | `harness/skills/gf-plan/SKILL.md` |
| 에이전트가 게임을 실행해 실제 화면을 봐야 한다 | `gf engine test/capture/bot/perf`. 게임 안의 브리지가 입력을 받고 상태를 돌려준다 | `harness/tools/gf/engine/`, `harness/templates/README.md` |
| 테스트 통과는 화면이 맞다는 뜻이 아니다 | 근거 규칙. 변경 뒤에 찍은 스크린샷과 통과 기록이 없으면 훅이 단계 승인을 막는다 | `harness/skills/gf-verify/SKILL.md`, `harness/hooks/guard.py` |
| 섞인 화면을 맥락 없는 심사자가 비교해야 자기 칭찬이 사라진다 | `gf judge pair`와 `blind-judge` 서브에이전트. 훅이 심사자가 심사 폴더 밖을 읽지 못하게 막는다 | `harness/tools/gf/judge/`, `harness/agents/blind-judge.md` |
| 과하게 다듬지 않으려면 멈추는 조건이 필요하다 | 멈춤 규칙. 게임 화면이 목표를 2번 이기면 그 방향은 끝낸다 | `harness/skills/gf-verify/SKILL.md` |
| 재미와 조작감은 사람만 판정했다 | `gf engine run --record`와 `replay`. 사용자의 플레이를 기록해 "느낌이 이상하다"를 재현한다 | `harness/tools/gf/play/` |
| 캐릭터 애니메이션, 소리, UI가 약점이다 | 설계 단계의 범위 점검표, UI와 소리 전용 스킬 | `harness/skills/gf-plan/SKILL.md`, `gf-ui`, `gf-audio` |
| 비용 수치는 자가 보고이고 편차가 크다 | 호출 전에 추정 비용을 계산하고 호출마다 비용 기록을 남긴다 | `harness/tools/gf/core/`, 게임 폴더의 `.gf/ledger.jsonl` |
| 특정 게임을 따라 만든 사례는 경계선에 있다 | 레퍼런스는 여러 출처에서 특성만 가져오고, 한 작품에 쏠리면 경고한다 | `harness/skills/gf-reference/SKILL.md` |

조사에 없던 장치도 있어요. 생성 모델을 **역할** 이름으로 부르는 규칙은 설계할 때 정했어요. 모델은 자주 은퇴하기 때문에 코드에 모델 ID를 적지 않고 설정 파일(`harness/tools/gf/core/defaults.toml`)에만 둬요.

## 하네스가 해 주지 못하는 일

하네스는 품질을 보장하지 않아요. 저장소가 직접 적은 한계예요(`harness/README.md`의 "알려진 한계").

- 재미, 조작감, 소리의 느낌은 사람만 판정할 수 있어요. 에이전트는 실행하고, 찍고, 재고, 물어요.
- 가까이서 보는 3D 인물 애니메이션은 여러 번 다시 만들어도 어색할 수 있어요.
- 이 방법이 확인된 범위는 작은 레벨, 짧은 한 판, 스타일이 뚜렷한 게임이에요.

cat-angler도 이 한계를 그대로 겪었어요. 하네스의 절차를 모두 따랐는데도 사용자에게 두 번 반려당했어요. 그 과정은 [cat-angler 제작 과정](cat-angler-case-study.md)에 있어요.

## 정리

- 조사가 먼저였고, 하네스는 조사 결과를 강제하는 수단이에요.
- 품질을 가른 것은 생성 모델의 성능보다 "실행해서 보고, 남이 심사하고, 사람이 플레이한다"는 검증 순서였어요.
- 프롬프트는 부탁이고 하네스는 구조예요. 건너뛰면 안 되는 일은 명령과 훅으로 만들어요.
