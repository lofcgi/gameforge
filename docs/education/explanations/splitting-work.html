에이전트 작업 분할 원칙

이 문서를 읽으면 큰 작업을 여러 에이전트에게 나눠 줄 때 무엇을 먼저 정해야 하는지, 그리고 나눠 만든 것이 왜 합치는 순간에 깨지는지 설명할 수 있어요. gameforge 하네스와 cat-angler는 둘 다 여러 제작 에이전트가 동시에 만들었어요. 그때 쓴 네 가지 원칙과, 원칙을 지켰는데도 생긴 결함을 실제 사례로 다뤄요.

지시서를 실제로 쓰는 절차는 제작 에이전트 작업 지시서 쓰기에 따로 있어요.

나눠 만들면 생기는 문제

제작 에이전트는 자기 맥락만 알아요. 메인 세션이 "생성기를 만들어 줘"라고만 하면 에이전트마다 출력 형식, 경로, 좌표 기준을 각자 정해요. 각자의 테스트는 통과하지만 합치면 맞물리지 않아요.

보고에도 문제가 있어요. 제작 에이전트의 보고는 성공한 일과 추측한 일을 같은 말투로 전해요. 메인 세션은 제작 에이전트가 일하는 모습을 보지 못하고 요약만 받기 때문에 둘을 구분할 수 없어요.

네 가지 원칙은 이 두 문제를 줄이려는 거예요.

 1. 계약 문서를 먼저 쓴다 ──► 2. 공용 부분을 메인 세션이 먼저 만든다
                                          │
        ┌─────────────────────────────────┼──────────────────────────────┐
        ▼                                 ▼                              ▼
   제작 에이전트 A                   제작 에이전트 B                 제작 에이전트 C
   (자기 폴더만 쓴다)                (자기 폴더만 쓴다)              (자기 폴더만 쓴다)
        │                                 │                              │
        └────── 3. 실행해서 확인한 것과 미확인 목록을 나눠 보고한다 ───────┘
                                          │
                                          ▼
                       4. 일찍 합쳐서 처음부터 끝까지 돌려 본다

원칙 1. 계약 문서를 먼저 쓴다

계약 문서는 따로 만든 결과가 맞물리도록 미리 정해 둔 약속이에요. 하네스의 계약 문서는 harness/AGENTS.md예요. 제작 에이전트를 띄우기 전에 세 가지를 정했어요.

  • 디렉터리와 소유권: gf/gen/은 생성기, gf/post/는 후처리, gf/engine/은 엔진 어댑터처럼 폴더마다 주인을 정했어요. "다른 소유자의 디렉터리는 수정하지 않는다. 공용으로 필요한 것은 gf/core/에 있고, 없으면 보고한다"는 규칙도 함께 적었어요.
  • 명령 규약: 모든 명령이 gf --project <게임 폴더> <그룹> <명령> 형태를 따라요.
  • 출력 규약: 성공하면 마지막 줄에 {"ok": true, "files": [...]}를, 실패하면 {"ok": false, "error": "..."}를 내요.

cat-angler를 다시 만들 때의 계약 문서는 games/cat-angler/design/asset-spec.md예요. 첫 문단이 목적을 그대로 말해요.

코드와 그림을 따로 만들어도 맞물리게 하는 계약이다. 그림은 이 경로와 크기로 만들고, 코드는 이 경로에서 읽는다. 바꿔야 하면 이 문서를 먼저 고친다.

이 문서에는 파일 경로(assets/game/chars/cat_idle.tres), 캔버스 크기(고양이 80×60), 기준점(발밑 가운데), 프레임 수가 적혀 있어요. 그림 담당과 코드 담당은 서로의 작업을 보지 않고 이 문서만 보고 일했어요.

원칙 2. 공용 부분은 메인 세션이 먼저 만든다

모두가 기대는 부분을 제작 에이전트에게 나눠 맡기면 서로 다른 버전이 생겨요. 하네스에서는 메인 세션이 공용 코어(gf/core/: 설정, 단계 상태, 비용 기록, fal 클라이언트, 출력 규약)를 먼저 쓰고 실제로 돌려 본 뒤에 제작 에이전트를 띄웠어요(세션 기록).

그다음 작업을 이렇게 나눴어요(세션 기록).

제작 에이전트 맡은 범위
A 생성기, 후처리, Blender
B 엔진 어댑터, 플레이 봇, 템플릿 네 개
C 레퍼런스, 블라인드 심사 준비
D (마지막) 플러그인 층(스킬, 서브에이전트, 훅)

플러그인 층을 마지막에 둔 이유는 스킬이 gf 명령을 인용하기 때문이에요. CLI가 완성된 뒤에 실제 --help 출력을 보고 써야 없는 옵션을 적지 않아요.

원칙 3. 실행한 것과 미확인 목록을 나눠 보고받는다

각 작업 지시서에는 세 가지를 적었어요(세션 기록).

  • 무엇을 소유하는지
  • 무엇을 실제로 실행해서 확인해야 하는지
  • 확인하지 못한 것을 따로 적어 보고할 것

세 번째가 핵심이에요. 미확인 목록을 요구하지 않으면 제작 에이전트는 "완료"라고만 보고해요. 요구하면 이런 문장이 돌아와요. 아래는 저장소에 남아 있는 실제 미확인 목록이에요(demo-check/EVIDENCE.md).

  • "소리는 길이와 음량만 쟀다. 듣지 못했다. 음악이 매끄럽게 반복되는지도 모른다."
  • "움직임의 느낌(걷기 속도와 이동 속도의 어울림, 발 미끄러짐)은 정지 화면으로만 봤다."
  • "키보드를 손으로 누르지 않았다. 보낸 키는 프로세스의 이벤트 큐에 직접 넣은 것이라 키보드 하드웨어와 창 포커스 판단을 거치지 않는다."

이 목록이 다음 작업의 출발점이 됐어요. 예를 들어 "음악이 매끄럽게 반복되는지 모른다"는 한 줄이 뒤에 이음매를 재는 검사와 고치는 명령으로 이어졌어요.

원칙 4. 일찍 합쳐서 끝까지 돌려 본다

각 부분이 자기 테스트를 통과해도 함께 돌려 본 적이 없으면 통과한 것이 아니에요. 하네스에서는 이 사실을 세 번 확인했어요.

통합 점검: 모듈 사이의 틈

부분들을 처음 함께 돌린 통합 점검에서 모듈 사이의 틈 일곱 개를 고쳤어요. 개수와 "합치기 전"의 모습은 세션 기록이고, "합친 뒤"의 모습은 표에 적은 저장소 위치에서 확인할 수 있어요. 두 가지 예시예요.

틈 합치기 전 합친 뒤 고친 것
3D 모델의 정면 방향 생성 모델, Blender 정리, 두 엔진 템플릿이 "앞"을 서로 다르게 가정했어요 규약을 한 곳(harness/templates/README.md 7절)에만 적었어요: GLB의 정면은 +Z, 생성 모델은 정면이 +X로 나오므로 gf blender rescale --turn -90으로 돌려요
비용 한도 단가를 계산할 수 없는 모델의 호출이 한도 검사를 그냥 통과했어요 --estimate-usd나 --allow-unknown-cost를 명시해야만 호출돼요(harness/tools/gf/core/fal.py)

조합 점검: 돌려 보지 않은 조합

엔진과 스타일의 조합 가운데 세 가지(Godot + 비픽셀 2D, 웹 + 픽셀 2D, 웹 + 비픽셀 2D)는 끝까지 돌려 본 적이 없었어요. 실제 생성물로 돌리자 결함 아홉 개가 더 나왔어요(개수는 세션 기록, 점검 결과는 demo-check/EVIDENCE.md D~G절). 두 가지 예시예요.

  • 비픽셀 스타일 프로젝트가 픽셀 아트용 화면 설정을 그대로 썼어요. 지금은 gf init --style 2d가 템플릿을 복사한 뒤 고해상도 2D용 설정으로 고쳐요(harness/templates/README.md 8절).
  • 웹 템플릿이 하네스가 만든 스프라이트 시트를 읽지 못했고 소리를 재생할 길이 없었어요.

미확인 전수 점검: 진짜 환경에서 써 보기

마지막으로 "확인하지 못한 것"을 전부 모아 하나씩 실제로 확인했어요. 가장 뼈아픈 결과는 스킬이었어요. 플러그인을 실제 Claude Code 세션에 불러와 평범한 말로 요청해 보니 스킬 13개 중 12개가 발동하지 않았어요(세션 기록). 스킬 설명이 "이 스킬은 무엇을 한다"만 말하고 "어떤 요청에 써야 하는지"를 말하지 않았기 때문이에요. 설명을 다시 썼고, 지금의 설명은 이런 형태예요(harness/skills/gf-assets-pixel/SKILL.md).

픽셀 아트 스프라이트, 도트, 타일셋, 픽셀 캐릭터 걷기 애니메이션을 만들어 달라거나 "픽셀이 뭉개진다/흐리다/크기가 안 맞는다"를 고쳐 달라는 요청에는, 직접 그리거나(SVG, Pillow, 코드) 생성 명령을 바로 부르기 전에 먼저 이 스킬을 쓴다.

이것도 끝난 일이 아니에요. 인계 기록은 "스킬 13개 중 자연어 발동을 실제 세션에서 다시 확인한 것은 3개"라고 적어요(.claude/handoffs/2026-11-23-gameforge-cat-angler.md).

합성 테스트와 실제 실행의 차이

세 번의 점검에서 공통으로 드러난 것은 가짜 입력으로 만든 테스트는 진짜 입력의 성질을 모른다는 점이에요. 단위 테스트는 사람이 예상한 입력으로 만들어요. 생성 모델과 운영체제는 예상하지 않은 입력을 줘요.

테스트가 가정한 것 실제로 온 것
픽셀 아트의 격자는 정수 픽셀이다 512픽셀 그림에 100칸, 칸 하나가 5.12픽셀
영상 프레임의 가장자리는 정지 그림과 같다 압축 때문에 배경의 초록이 외곽선으로 번짐
3D 모델의 면은 이어져 있다 면이 떨어져 있어서 삼각형 수를 줄이자 구멍이 남
눌러 둔 키는 계속 눌려 있다 앱이 포커스를 잃으면 Godot이 눌린 키를 전부 뗌

이 사례들의 원인과 고친 방법은 실패 사례 목록에 있어요.

cat-angler에서 달라진 점

cat-angler를 다시 만들 때는 세 제작 에이전트가 화면 구조, 그림과 소리, 컷신을 나눠 맡았어요(.claude/handoffs/2026-11-23-gameforge-cat-angler.md). 하네스를 만들 때 배운 것을 두 가지 반영했어요.

  • 계약 문서에 "없을 때의 동작"을 넣었어요. 코드는 그림 파일이 없으면 도형으로 그린 임시 그림을 쓰고, 빠진 파일 이름을 목록(F3 키)에 올려요. 파일을 넣으면 코드 수정 없이 다음 실행부터 쓰여요(games/cat-angler/design/asset-spec.md). 그래서 코드 담당과 그림 담당이 서로를 기다리지 않았어요.
  • 계약을 고친 쪽이 문서에 흔적을 남겼어요. asset-spec.md에는 "(코드 쪽에서 추가)", "(코드 쪽에서 정함)" 표시가 있어요. 일하다가 약속을 바꿔야 하면 문서를 먼저 고쳤어요.

그래도 틈은 남았어요. 그림 담당의 상태 문서(games/cat-angler/design/asset-status.md)는 고양이 캔버스가 규격(48×56)과 다른 80×60이 됐다고 적고, 여러 에셋에 "게임 화면에서 확인하지 못했다"고 적어요.

정리

  • 계약 문서(경로, 크기, 출력 형식, 소유권)를 제작 에이전트보다 먼저 만들어요.
  • 모두가 기대는 부분은 메인 세션이 먼저 만들고 실행해 봐요.
  • 보고는 "실행해서 확인한 것"과 "미확인 목록"으로 나눠 받아요.
  • 부분의 테스트 통과를 믿지 말고, 일찍 합쳐서 진짜 입력으로 끝까지 돌려요.
