문제 해결 (How-to 가이드)

설계 인터뷰 하기

이 가이드를 따라 하면 사용자의 한 문단짜리 아이디어를, 구현 전에 결정이 닫힌 설계 요약(design/brief.md)으로 바꿀 수 있어요. 에이전트가 범위를 줄이다가 "너무 단순한 게임"을 내놓는 실수를 막는 것이 목표예요.

이럴 때 쓰세요

  • 사용자가 준 아이디어가 한두 문장뿐일 때
  • 에이전트가 쓴 설계가 사용자의 기대보다 훨씬 작게 나올 때
  • 구현 도중에 "그건 정한 적 없는데"가 반복될 때

cat-angler의 첫 설계는 모든 것을 고정된 한 화면에 넣었고, 사용자는 "너무 단순하다"며 반려했어요. 같은 장르의 다른 게임은 배를 몰아 옆으로 멀리 나갈 수 있는데 그것이 빠졌기 때문이에요. 사용자가 남긴 요청은 두 가지였어요(.claude/handoffs/2026-11-23-gameforge-cat-angler.md).

  • 설계를 단순하게 줄이지 말 것
  • 기획은 사용자가 말한 대로 받아 적지 말고 인터뷰식으로 잡을 것

준비하기

  • 게임 프로젝트가 plan 단계여야 해요. gf state show로 확인하세요.
  • 설계 요약의 틀은 harness/skills/gf-plan/brief-template.md에 있어요.
  • 이 가이드는 에이전트(메인 세션)가 사용자에게 묻는 절차예요. 사람이 혼자 기획할 때는 질문에 스스로 답하면 돼요.

1. 받아 적지 않고 묻기

사용자의 문단을 그대로 문서로 옮기지 마세요. 아이디어에서 아직 정해지지 않은 결정을 찾아 질문으로 바꾸세요. 하네스의 설계 스킬이 정한 기본 질문은 다섯 가지예요(harness/skills/gf-plan/SKILL.md).

  1. 플레이어는 무엇을 하는가 (동사 하나)
  2. 왜 한 판 더 하고 싶은가
  3. 한 판은 얼마나 긴가, 어떻게 이기고 지는가
  4. 꼭 있어야 하는 것 한두 가지, 절대 원하지 않는 것
  5. 얼마나 걸려서 누구에게 보여 줄 것인가

이미 들은 것은 다시 묻지 마세요. 한 번에 최대 다섯 개만 물으세요.

2. 객관식으로 묻고 추천안 붙이기

열린 질문("바다는 어떤 구조가 좋을까요?")은 사용자에게 설계를 떠넘겨요. 결정을 가르는 선택지를 만들고, 추천안과 그 선택의 대가를 함께 보여 주세요. cat-angler에서 쓴 방식이에요(세션 기록).

질문 하나의 형태는 이래요. 내용은 cat-angler의 닫힌 결정(games/cat-angler/design/brief.md)을 질문으로 되돌려 쓴 예시예요.

바다의 구조를 어떻게 할까요?

 A. 하나로 이어진 긴 바다를 좌우로 항해한다 (추천)
    얻는 것: 멀리 나갈수록 달라지는 풍경, "조금만 더 나가 볼까"라는 갈등
    대가: 빈 구간이 생기지 않도록 채울 볼거리가 필요하다
 B. 구역을 골라 이동하는 지도 화면
    얻는 것: 만들 화면이 적다
    대가: 항해하는 느낌이 사라진다
 C. 고정된 한 화면
    얻는 것: 가장 빨리 만든다
    대가: 같은 장르의 다른 게임보다 단순해 보인다

사용자가 답하지 않으면 추천안을 내고 "이대로 갈까요?"로 닫으세요.

3. 같은 장르의 기본기와 비교하기

범위를 줄이기 전에, 그 장르의 게임이라면 당연히 있는 것을 목록으로 적으세요. 하네스의 설계 스킬은 넓은 범위를 경고하지만(harness/skills/gf-plan/SKILL.md의 범위 점검표), 그 경고는 "장르의 기본기까지 빼라"는 뜻이 아니에요.

구분 줄여도 되는 것 줄이면 안 되는 것
양 레벨 수, 어종 수, 구간 수 장르가 약속하는 핵심 경험(낚시 게임의 "멀리 나간다")
시스템 보조 시스템의 개수 핵심 반복을 이루는 판단(어디서 낚을지, 언제 돌아올지)
연출 컷 수, 대사량 사용자가 꼭 있어야 한다고 한 것

특정 기존 게임을 다시 만들지는 않아요. 사용자가 게임 이름을 대면 그 게임에서 좋아하는 특성 세 개쯤을 말로 뽑고, 이름·캐릭터·레벨·화면 구성은 가져오지 마세요.

줄인 것은 버리지 말고 설계 요약의 "Out of scope"에 적으세요. cat-angler는 낮과 밤, 날씨, 별주부의 동행을 그 칸으로 보냈어요.

4. 결정을 닫아 설계 요약 쓰기

design/brief.md에 빈칸을 남기지 마세요. 정하지 못한 것은 "미정"으로 두지 말고 사용자에게 물어서 닫으세요. 반드시 들어가는 항목이에요.

항목 내용
한 문장 훅 "〈누가〉 〈어디서〉 〈무엇을 해서〉 〈무엇을 얻는〉 게임." 듣고 화면이 떠올라야 해요
핵심 반복 시작 → 플레이 → 이김/짐 → 재시작이 몇 초, 몇 분 단위인지
Keep / Avoid / Out of scope 끝까지 지킬 것, 하지 않을 것, 이번에는 안 만드는 것
닫힌 결정 카메라, 조작, 화면, 한 판 길이, 콘텐츠 수. 구현 중에 바꾸려면 사용자에게 다시 물어요
사람이 판정할 것 재미, 조작감, 소리처럼 에이전트가 숫자로 볼 수 없는 것
인수 기준 실행해서 확인할 수 있는 문장 (예: "봇이 여는 장면부터 닫는 장면까지 도달한다")

5. 반려 내용을 문서에 옮기기

사용자가 반려하면 대화로만 받지 말고 설계 요약의 문장으로 옮기세요. 다음 세션과 제작 에이전트는 대화를 보지 못하고 문서만 봐요. cat-angler의 설계 요약에는 반려에서 나온 문장이 이렇게 남아 있어요.

  • 피할 것: "빈 바다를 오래 이동만 하는 구간. 화면 두 개 너비 안에 항상 볼거리가 있어야 한다"
  • 닫힌 결정: "장면마다 그린 전체 화면 그림이 움직이는 컷신. 글 카드로 대신하지 않는다"
  • 화면 구성: "한 화면에 몰아넣지 않는다"

결과 확인하기

  • 설계 요약에 "미정"이 없어요.
  • 닫힌 결정 표의 모든 줄을 사용자가 읽고 동의했어요.
  • 같은 장르의 게임을 아는 사람이 읽고 "이건 왜 없지?"라고 물을 만한 것이 Keep이나 Out of scope 어느 한쪽에 적혀 있어요.
  • 근거 검사가 통과해요.
gf check evidence

설계 요약이 없으면 이 명령은 "design/brief.md 가 없거나 비었다"라는 problems와 함께 실패해요. 통과하고 사용자가 승인하면 gf state approve --note "<훅 한 줄>"로 다음 단계로 넘어가요.
