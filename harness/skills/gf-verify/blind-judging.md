# 블라인드 심사 절차

조건 세 가지가 전부다: **같은 카메라**, **섞인 순서**, **맥락 없는 새 심사자**.

## 1. 같은 조건의 두 화면을 준비한다

변경 전에 찍어 둔다. 변경 뒤에 같은 명령으로 다시 찍는다.

```sh
$GF engine capture --out captures/<작업>-before --script bot/<액션>.json --at 2.0 --seed 0
# ... 한 가지를 바꾼다 ...
$GF engine capture --out captures/<작업>-after  --script bot/<액션>.json --at 2.0 --seed 0
```

게임이 결정적이므로(같은 시드, 같은 입력) 두 화면은 바꾼 것만 다르다. 화면 비율이 다르면 `judge pair` 결과의 `aspect_mismatch` 가 true 가 된다. 그 쌍은 버리고 같은 `--size` 로 다시 찍는다.

## 2. 쌍을 만든다

| 방식 | `--a` | `--b` | 쓰는 때 |
|---|---|---|---|
| `change` (기본) | 수정 전 화면 | 수정 후 화면 | 변경 하나를 남길지 되돌릴지 정할 때. `--target design/look/frame.png` 를 함께 주면 "목표에 더 가까운 쪽"을 고르게 된다 |
| `target` | 목표 그림 | 게임 화면 | 게임 화면이 목표 수준에 왔는지 볼 때. `--target` 은 주지 않는다 |

```sh
$GF judge pair --a <a> --b <b> [--target <목표>] --mode <change|target> --id <쌍 이름> --series <묶음 이름>
```

- `--id` 는 영문·숫자·`._-`. 한 번 쓴 이름은 다시 못 쓴다(예: `fog-01`, `fog-02`).
- `--series` 는 승패를 함께 세는 묶음이다. 한 방향의 작업(예: `lighting`, `hud`, `vs-target`)마다 하나.
- 명령이 X.png / Y.png 순서를 무작위로 정하고, 원본 파일 이름과 메타데이터가 넘어가지 않게 다시 인코딩한다. 대응표는 `.gf/judge/` 에만 있다.

결과에서 쓰는 값: `judge_reads`(심사 폴더, 게임 폴더 기준), `files`(그 안의 파일들), `aspect_mismatch`.

## 3. 심사자를 부른다

`blind-judge` 서브에이전트(플러그인 이름이 붙어 `gameforge:blind-judge`)를 **매번 새로** 부른다. 프롬프트에는 이것만 넣는다:

```
아래 파일만 읽고 rubric.md 의 형식대로 답하라.
<게임 폴더>/captures/judge/<쌍 이름>/rubric.md
<게임 폴더>/captures/judge/<쌍 이름>/X.png
<게임 폴더>/captures/judge/<쌍 이름>/Y.png
<게임 폴더>/captures/judge/<쌍 이름>/target.png      (있을 때만)
```

넣지 않는 것: 무엇을 고쳤는지, 어느 쪽이 수정 후인지, 게임 설명, 기대하는 결과, 이전 심사 결과. 이런 말이 들어가면 심사가 무효다. 다시 다른 id 로 쌍을 만들어 심사한다.

중요한 판정(단계 승인 전, 큰 변경)은 심사자를 두 번 따로 불러 결과가 갈리면 `tie` 로 기록한다.

## 4. 기록한다

심사자가 낸 JSON 을 고치지 않고 넣는다. `scores` 는 `{"X": {...}, "Y": {...}}` 형태 그대로.

```sh
$GF judge record --id <쌍 이름> --winner <X|Y|tie> --scores '{"X": {...}, "Y": {...}}' --notes "<notes>"
```

결과에서 읽는 값:

| 값 | 뜻 | 할 일 |
|---|---|---|
| `winner` | `a` / `b` / `tie` 로 풀린 승자 | — |
| `keep_change` (change 방식) | 수정 후가 이기거나 비겼는가 | false 면 변경을 되돌린다 |
| `counts` | 이 묶음의 판 수, 승, 무, 패 | — |
| `stop.met`, `stop.reason` | 멈춤 조건 충족 | true 면 이 방향은 끝. 다음 작업으로 |
| `rules` | 지켜야 할 세 규칙 | 아래 |

```sh
$GF judge history --series <묶음 이름>      # 묶음별 승패 요약. 사용자에게 보여 줄 근거
```

## 세 규칙

1. **변경은 심사에서 이기거나 비겼을 때만 남긴다.** 지면 되돌린다. "그래도 내 생각엔 낫다"로 남기지 않는다. 사람(사용자)이 직접 보고 남기라고 하면 남긴다.
2. **목표 그림에 없다는 이유만으로 게임 화면의 요소를 지우지 않는다.** 목표는 느낌의 기준이지 내용물 목록이 아니다. 심사에서 이기려고 HUD·적·이펙트를 빼면 화면은 목표와 비슷해지고 게임은 나빠진다.
3. **멈춤 조건을 만족하면 더 다듬지 않는다.** `target` 방식은 게임 화면이 목표를 2번 이기면 끝, `change` 방식은 최근 2판 연속으로 수정 후가 이기지 못하면 그 방향은 끝이다. 과잉 폴리시를 막는다.

## 한계

- 심사는 정지 화면만 본다. 움직임, 조작감, 소리, 재미는 사람이 판정한다.
- 엄격한 기준에서는 좋은 화면도 5~6점이다. 점수를 올리는 것이 목표가 아니다.
- 같은 쌍을 원하는 결과가 나올 때까지 다시 심사하지 않는다. 기록은 한 번만 된다.
