# 공개 글과 커뮤니티 규칙

## 글의 틀 (`design/publish-post.md`)

```markdown
# 〈제목: 무엇을 만들었고 어떻게 — 과장 없이〉

플레이: 〈링크〉 (브라우저에서 바로, 가입 없음. 조작: 〈키〉)

〈한 문단: 어떤 게임인지, 한 판이 얼마나 긴지〉

## 만든 방법
- 기간: 〈N일/주〉, 엔진: 〈Godot / three.js〉
- 단계: 기획 → 룩 고정 → 그레이박스 → 에셋 → 폴리시
- 숫자: 플레이테스트 〈N〉회, 블라인드 심사 〈N〉판, 생성 비용 약 $〈N〉

## AI 가 한 것
- 코드: 〈모델·도구〉가 작성. 나는 〈리뷰/지시만〉
- 그림·모델: 〈이미지 모델〉로 생성 후 스크립트로 후처리(〈픽셀 격자 맞춤, 팔레트 통일 등〉)
- 소리: 〈효과음·음악 생성 모델〉
- 스크린샷·영상: 〈사람이 플레이 / 봇이 플레이한 화면임〉

## 내가 한 것
- 〈게임 아이디어와 규칙, 범위 결정〉
- 〈레퍼런스 고르기, 룩 승인, 반려한 것들〉
- 〈매 빌드 플레이하고 조작감·난이도 피드백〉
- 〈소리 듣고 고르기〉

## 잘 안 된 것
- 〈실패 하나 이상: 버린 프로토타입, 여러 번 반려한 애니메이션 등〉

## 아직 안 되는 것
- 〈알려진 버그, 지원 안 되는 브라우저〉
```

원칙:

- 링크가 맨 위. 영상·이미지만 올리지 않는다.
- 실제 플레이 장면을 쓴다. 봇이 찍은 것이면 먼저 밝힌다.
- 숫자는 프로젝트 기록에서 가져온다(`.gf/ledger.jsonl`, `gf state show`, `gf judge history`, `captures/sessions/`). 기억으로 쓰지 않는다.
- "AI 가 다 했다"도 "내가 다 했다"도 쓰지 않는다. 나눠서 쓴다.
- 기존 게임의 이름을 빌려 설명하지 않는다("○○ 클론"). 닮았다는 지적은 가장 흔한 비판이다.
- 영어 커뮤니티에는 영어로 쓴다. 번역은 에이전트가 돕되 사용자의 말투로 다듬는다.

## 커뮤니티 규칙 (2026-11 조사 시점. 올리기 전에 반드시 다시 읽는다)

| 곳 | 조사 시점의 규칙·분위기 | 할 일 |
|---|---|---|
| r/aigamedev | 게임 홍보 글은 **AI 로 어떻게 개발했는지**의 맥락으로 써야 한다. 글 없는 영상·이미지, 기계적인 불릿 목록은 삭제될 수 있다. 판매 중인 게임은 "Commercial Self Promotion" 플레어. 영어만 | 과정·숫자·실패를 본문에. 판매 게임이면 플레어 |
| r/ClaudeAI | "정확히 어떻게 만들었는가" 형식의 워크플로 글이 잘 받아들여진다 | 방법 중심으로 |
| r/godot | "No AI" 규칙: AI 가 만든 글뿐 아니라 **프로젝트·스크린샷·영상·아트·코드**에도 적용 | AI 로 만든 게임은 올리지 않는다 |
| 일반 gamedev 계열 서브 | AI 사용을 밝히자 삭제된 사례가 있다. 서브마다 다르다 | 규칙 원문을 읽고, 금지면 올리지 않는다 |
| Steam | AI 생성 콘텐츠 공시 양식이 있다. 공시 문구가 이용자 반응의 중심이 된 사례가 있다 | 규정대로 공시하고 반응을 예상해 둔다 |
| itch.io | 게임 페이지에 생성 AI 사용 여부를 표시하는 항목이 있다(현재 형식은 올릴 때 확인) | 사실대로 표시 |

규칙 확인 방법: 해당 커뮤니티의 규칙 페이지(예: `https://old.reddit.com/r/<서브>/about/rules`)를 그날 직접 읽는다. 이 표는 낡았을 수 있다. 에이전트는 규칙을 요약해 주고, 올릴지 말지는 사용자가 정한다.

## 반응에서 배우는 것

칭찬은 분위기, 디테일, 반복한 흔적, 바로 플레이됨, 투명한 공개에 몰린다. 비판은 게임플레이 없음, 조작감, 어색한 애니메이션, 기존 게임과의 유사성, 기술 결함(브라우저 죽음, 로딩 멈춤), 홍보성 서사에 몰린다. 받은 지적은 `design/playtest-notes.md` 에 모은다.
