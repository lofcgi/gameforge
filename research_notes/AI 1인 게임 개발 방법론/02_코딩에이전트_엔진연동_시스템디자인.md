### Inferences
- 기간 내 자료만 보면 에이전트는 **Claude Code가 사실상 기본값**이고 Codex는 보조(목업, 팀원 한 명의 도구)로 등장한다. Cursor, Gemini CLI를 주 도구로 쓴 실무자 1차 사례는 기간 내에 찾지 못했다(Epic/Unity 공식 도구가 이들을 지원 클라이언트로 명시할 뿐이다).
- 여러 devlog가 공통으로 보여 주는 "잘 되는 이유"는 엔진의 텍스트 포맷이 아니라 **검증 루프**다: 에이전트가 게임을 띄우고, 봇이 플레이하고, 스크린샷/테스트로 결과를 스스로 확인한다. Unreal은 5.8~5.9에서 공식 MCP + Python이 이 루프를 제공하면서 실용 범위에 들어온 것으로 보인다.
- Unreal에서도 실무자들은 Blueprint보다 **C++ + 코드로 생성하는 에셋**(commandlet, Python 스크립트)을 선호하는 경향이 있다(Dust & Thunder, SkyCut, THE BOSS THEY CUT). 바이너리 에셋은 머지가 안 되기 때문이다(Forest Barrier가 명시).

### Gaps
- Unity + 에이전트로 **기간 내에** 게임을 만든 실무자 1차 devlog/postmortem은 찾지 못했다(도구 릴리스만 확인, 질문 2 참조).
- Godot + 에이전트의 기간 내 실무자 1차 사례(출시작, 플레이어 수 포함)를 찾지 못했다. Godot 우위론의 독립적 근거는 기간 외 자료뿐이다.
- 엔진별 사용 비율을 보여 주는 설문/통계는 기간 내에 없다. "가장 많이 쓰인다"는 정량 주장은 할 수 없다.
- MegaJam 출품작들의 품질 평가(수상, 평점)는 미발표다.

## 2. 지금 인기 있는 엔진 MCP 서버 / 플러그인 / 스킬은? (이름, 저장소, 별 수, 기간 내 릴리스)

## 3. 성공한 실무자들은 GDD·스펙·컨텍스트 파일을 어떻게 구성해 긴 프로젝트에서 에이전트 일관성을 유지하는가?

### Takeaway
기간 내 실무자들이 공통으로 쓰는 구조는 "**계약 문서 먼저(공유 타입·인터페이스·파일 소유권) → lane/worktree별 서면 브리프 → 스크린샷 기반 리뷰**"이며, GDD 자체는 짧게 유지하고 결정·인계 기록을 별도 파일로 쌓는다. 문서를 많이 쓰는 것이 더 좋은 게임을 만든다는 근거는 없고, 오히려 반대 사례가 보고된다.

## 4. AI를 게임 시스템 디자인과 밸런싱에 어떻게 쓰는가? (시뮬레이션, 자동 튜닝, 데이터 주도 설정)

### Takeaway
기간 내 실무자들의 밸런싱은 정교한 자동 튜닝이 아니라 "**계측 가능한 격리 테스트 + 플레이 봇 + 사람의 최종 판단**"이다. 능력별 격리 측정(20초간 처치 수), 로그 기반 비행 모델 튜닝, 봇 승률 비교가 대표적이고, 대규모 Monte Carlo 시뮬레이션은 도구(ReignsAgent)와 기간 외 사례에서만 확인된다.

### Inferences
- 밸런싱을 에이전트에게 맡기려면 먼저 **게임 규칙을 렌더러와 분리된 결정론적 코어**로 만들어야 한다. ReignsAgent의 구조(헤드리스 코어 + 독립 시뮬레이터 + 제안/검증 흐름)와 기간 외 TCP 브리지 사례가 같은 방향을 가리킨다.

- 봇은 사람이 겪는 문제를 숨긴다(키를 계속 누름, 마우스 미사용, 실수로 트리거). 따라서 봇 지표는 회귀 방지용이고, 재미/타격감/난이도 곡선의 결정은 사람 플레이에 남는다.

### Gaps

- Godot는 공식 MCP/에이전트 통합이 없는 유일한 주요 엔진으로 남아 있고(이해관계 글의 주장), 커뮤니티 서버가 그 공백을 메우고 있다.

### Gaps
- Epic의 원문 발표(unrealengine.com/news, 공식 Rules PDF, 포럼 FAQ)는 직접 열람하지 않았다. 위 Epic 관련 날짜·규칙은 3자 요약과 참가자 devlog에 의존한다.
