## 질문 1. 최근 한 달간 실무자가 보고한 자동 플레이테스트/QA 루프는 무엇이고, 어떤 도구를 쓰며, 얼마나 효과적인가?

### Takeaway
기간 내 1차 기록들이 같은 결론을 낸다. 봇과 에이전트는 "게임이 동작하는가"(크래시, 막힘, 상태 회귀)는 잘 잡지만 "재미있는가, 화면에 실제로 그렇게 보이는가"는 잡지 못한다. 그래서 실무자들은 (1) 커밋마다 결정론적 headless 스크립트/봇, (2) 실제 입력 경로와 화면 픽셀을 측정하는 검증, (3) 사람 플레이테스트를 최종 판정으로 두는 3층 구조를 쓴다.

**B. 브라우저 게임 + headless 브라우저 하네스 (개발자 본인 기록, [공식/1차])**

- Phaser 기반 벨트스크롤 액션 게임에서 AI 개발 파트너 "Muse"(기반 모델 미공개)가 headless 브라우저로 실제 게임을 띄우고 연습 모드에서 키보드와 터치 이벤트로 플레이한다. 테스트는 고정 sleep이 아니라 게임 상태(던진 적이 착지했는지)를 기다린다. headless에서 프레임레이트가 떨어지기 때문이다. 게시일 11월 7일(연도는 헤더에 없어 2026으로 추정, 미확인). — [Muse vs. the Game](https://dev.to/wabiplant/muse-vs-the-game-teaching-an-ai-agent-to-playtest-my-beat-em-up-oif)
- 같은 글의 실패 3건: (1) 합성 키보드 이벤트가 게임의 입력 핸들러에 닿지 않아 깨진 입력에서도 테스트가 통과했다. 프로덕션 입력 경로를 강제해 해결. (2) 애니메이션 개편 후 상태 머신 검사는 통과하고 보고서도 "반영됨"이었지만 실제 폰에서는 실루엣이 거의 픽셀 동일해 변화가 없었다. (3) 스냅샷 API가 빈 버퍼를 반환하면 0픽셀 비율이 "1.000"(완전 일치)으로 나왔다. 최소 콘텐츠 픽셀 수 조건을 추가. — [같은 글](https://dev.to/wabiplant/muse-vs-the-game-teaching-an-ai-agent-to-playtest-my-beat-em-up-oif)
- 그 뒤의 완료 기준: 스프라이트 시트는 게임에 넣기 전에 발 너비·키·접지선을 측정해 기준 미달이면 거부하고, 인게임 스크린샷으로 포즈별 폭과 공격 리치를 측정하고, 폰 해상도·픽셀 밀도를 에뮬레이션해 가로/세로 양방향으로 돌린다. 양방향 테스트가 없는 스위트는 커버리지 체커가 실패시킨다. 비용·시간 수치는 없다. — [같은 글](https://dev.to/wabiplant/muse-vs-the-game-teaching-an-ai-agent-to-playtest-my-beat-em-up-oif)

**C. Godot 자동 플레이테스트 방법 비교 ([벤더] Ziva, 2026-11-05 게시·11-09 수정, 확인)**

- 권장 조합은 커밋마다 스크립트 검사, 출시 전 에이전트 패스다. 스크립트/봇은 무료·반복 가능·빠르지만 스크립트한 것만 검사하고, AI 에이전트는 스크립트 밖 경로를 찾지만 모델 시간이 들고 실행마다 결과가 달라진다. — [How to automate playtesting in Godot](https://dev.to/ziva/how-to-automate-playtesting-in-godot-simulated-input-bots-mcp-servers-and-ai-agents-4cb1)
- 저자가 심어 둔 버그(점수 라벨 미발견)를 대상으로 직접 돌린 결과: GUT는 `godot --headless --path . -s addons/gut/gut_cmdln.gd -gdir=res://test -gexit`로 실행해 exit code 1, GdUnit4 6.2.3은 `--ignoreHeadlessMode`가 필요하고(없으면 exit 103) 실패 시 exit 100이었다. — [같은 글](https://dev.to/ziva/how-to-automate-playtesting-in-godot-simulated-input-bots-mcp-servers-and-ai-agents-4cb1)
- 봇 autoload 방식: `godot --headless --path . --fixed-fps 60 --quit-after 600 -- --bot`. 게임 시간 2초를 실시간 0.78초에 돌렸고 실행 간 움직임이 동일했다. `--quit-after`는 멈춘 실행이 CI를 붙잡는 것을 막는다. — [같은 글](https://dev.to/ziva/how-to-automate-playtesting-in-godot-simulated-input-bots-mcp-servers-and-ai-agents-4cb1)
- 함정 3가지: Godot는 `SCRIPT ERROR`가 나도 exit 0으로 끝나므로 봇이 직접 pass/fail을 정해야 한다. GdUnit4의 프레임 기반 대기(`simulate_frames(72)`)는 headless에서는 통과했지만 `xvfb-run`에서 3회 중 3회 실패해 시간 기반(`await_millis(1200)`)으로 바꿨다. `--write-movie`는 `--headless`와 함께 쓰면 signal 11로 크래시했다. — [같은 글](https://dev.to/ziva/how-to-automate-playtesting-in-godot-simulated-input-bots-mcp-servers-and-ai-agents-4cb1)
- Claude Code/Cursor용 Godot MCP 서버 목록(가격·기능은 각 벤더 페이지 자기 신고): Godot MCP Pro($15 일회, 입력 시뮬레이션·상태 assertion·랜덤 입력 스트레스 테스트 주장), GDAI MCP($19 일회, Ziva 공동창업자 제작), Beckett(Lite 무료 / Full $15, 녹화·재생과 headless CI 러너), satelliteoflove/godot-mcp(무료, freeze/step과 JSON 상태), Godot AI(무료, `input_sequence`), Erodenn/godot-mcp-runtime(무료, `simulate_input`·`take_screenshot`), Coding-Solo/godot-mcp(무료, 입력·스크린샷 도구 없음). — [같은 글](https://dev.to/ziva/how-to-automate-playtesting-in-godot-simulated-input-bots-mcp-servers-and-ai-agents-4cb1)
- Ziva 자체 제품: `run_scene`은 에디터에서 씬을 실행해 스크린샷·콘솔·런타임 에러를 반환한다. Full Game Playtest Agent(Pro $50/월)는 목표를 향해 플레이하며 모델이 생각하는 동안 게임을 멈추고 입력을 하나씩 보내 pass/fail/blocked를 낸다. 한계로 headless/CI 모드 없음, 키보드·마우스만 지원, export 빌드·모바일·웹 불가, "재미는 판정하지 않음"을 스스로 명시한다. `run_scene`은 대상이 없는 클릭을 `delivered: false`로 보고하면서도 전체 실행은 success로 보고했다. — [같은 글](https://dev.to/ziva/how-to-automate-playtesting-in-godot-simulated-input-bots-mcp-servers-and-ai-agents-4cb1)
- 화면만 보고 동작하는 블랙박스 AI QA 에이전트로 modl.ai, nunu.ai가 언급되지만 가격과 성능 수치는 없다. — [같은 글](https://dev.to/ziva/how-to-automate-playtesting-in-godot-simulated-input-bots-mcp-servers-and-ai-agents-4cb1)

### Inferences
- 세 건의 독립된 1차 기록(Rejected Hero, IN FRAME, Muse)이 같은 실패 유형을 보고한다. 상태값 검사는 통과하는데 화면은 다르다는 것이다. 따라서 "봇 PASS"와 "사람이 본 결과"를 보고서에서 분리해 적는 규칙이 실무 표준으로 굳어지는 중이라고 볼 수 있다.
- 효과가 수치로 입증된 영역은 결정론적 headless 시뮬레이션과 회귀 테스트다. 범용 vision/computer-use 에이전트가 게임을 자유롭게 플레이해 버그를 찾는 방식은 기간 내에 성능 수치가 없고 벤더 주장뿐이다.
- 합성 입력이 실제 입력 경로를 타는지 확인하는 것, exit code를 엔진에 맡기지 않는 것, 프레임 수 대신 시간/상태 기반 대기가 공통된 구체적 함정 회피책이다.

### Inferences
- 기간 내 근거로 보면 병목은 코드 생산이 아니라 (1) 사람의 감각 판정 대역폭, (2) 플랫폼별 빌드·심사·QA, (3) 발견성과 마케팅이다. 이 셋은 콘텐츠 양이 늘수록 선형 이상으로 커지므로, AAA 스코프는 "코드를 더 빨리 쓰는 것"으로 닿지 않는다. 이것은 조사자의 추론이고 이를 직접 주장한 기간 내 비평가 글은 없다.
